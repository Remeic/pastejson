# PasteJSON measured performance changes

The root-string model, Text HTML generation, and Min preparation for small inputs are faster. The ordinary 5 MiB record input has no repeatable gain from paste to the first browser Paint event.

## Test conditions

Test date: 2026-10-03. Baseline: `3d7c29a6f999c105fed620735da51ff6ee475151`. Machine: Apple M4, 16 GB, macOS kernel 25.5.0. Engines: Bun 1.3.14 and Chrome 153.0.8010.53.

Source SHA256: `f10a17f6efd6a34b428d8fd802ef0f0c81a4192034db2e71d94a9dd4e2fa1728`.

The suite covers 11 input shapes: the existing 5 MiB record fixture, integer and float arrays, string arrays, escaped keys and values, a long string in an object, unique keys, a root string, and three smaller inputs. These are synthetic inputs measured on the machine, with identical data before and after.

Bun uses three separate processes per version, in AB/BA order. Each process uses 32 warmup samples and 21 measured samples per step. The result is the median of 63 samples. Chrome uses 32 warmup pairs and 41 measured pairs in alternating AB/BA order. A second Chrome run checks repeatability. Short inputs use batches of 200 operations; Text HTML uses batches of 100.

The paired Bun method gave large differences on escaped keys and unique keys. An unchanged-code calibration and separate-process checks showed that the method affected the result. The Bun release evidence therefore uses separate processes. The JIT cause was not established.

## Component results

These are computation times. They exclude DOM insertion and browser layout.

| Engine and operation | Before | After | Time reduction |
| --- | ---: | ---: | ---: |
| Chrome root string model, 5 MiB | 4.845 ms | 2.085 ms | 57.0% |
| Bun root string model, 5 MiB | 5.959 ms | 0.528 ms | 91.1% |
| Chrome Text HTML, 64 record rows | 5.200 us | 4.450 us | 14.4% |
| Chrome Text HTML, 64 unique-key rows | 7.300 us | 5.350 us | 26.7% |
| Chrome Min preparation, small input | 0.875 us | 0.350 us | 60.0% |
| Bun Min preparation, small input | 0.961 us | 0.212 us | 77.9% |

The second Chrome run measured 57.5%, 15.5%, 24.1%, and 55.6% reductions for the corresponding Chrome rows. Text HTML gains apply to a window near the document midpoint. A single long line has no material HTML gain.

Root scalar values now use the length and first character of native `JSON.stringify` output. They need one token and one line offset. The 5 MiB root-string fixture reserves **31,457,420 bytes before and 12 bytes after** for these two buffers. This measures ArrayBuffer capacity, not resident process memory.

Text rows now use one binary search per window and a forward token cursor. Short tokenization inputs reserve at most two integers per source character. Larger inputs keep the existing seed and growth rules. Container buffer capacities and the value walk remain in place.

## Complete pipeline results

The compute pipeline includes parse, model construction, and the first 64 Text rows. It excludes textarea work, Worker startup and transfer, DOM insertion, and layout.

| Chrome input | Before ms | After ms | Time change |
| --- | ---: | ---: | ---: |
| 5 MiB records | 17.115 | 17.215 | +0.6% |
| 250,000 integers | 4.420 | 4.170 | -5.7% |
| 100,000 floats | 5.690 | 5.795 | +1.8% |
| 100,000 strings | 3.795 | 3.790 | -0.1% |
| 50,000 escaped records | 14.605 | 14.530 | -0.5% |
| 5 MiB string in an object | 5.405 | 5.210 | -3.6% |
| 50,000 unique keys | 11.970 | 11.970 | 0.0% |
| 5 MiB root string | 5.375 | 1.490 | -72.3% |
| Medium records | 0.036900 | 0.036475 | -1.2% |
| Dense small array | 0.020525 | 0.020200 | -1.6% |
| Small input | 0.001450 | 0.001425 | -1.7% |

Positive time change means slower. The repeat record result was +0.9%; no record-pipeline gain is claimed. Large Min timings varied: the string-array result was +10.0% in the first Chrome run and +1.5% in the repeat. Only the small-input Min gain is repeatable.

The production-build test pastes through the clipboard handler and includes the Worker and DOM. It uses three warmup pastes and 11 measured pastes per version. Chrome tracing measures the end of the first main-thread Paint event after the formatted rows are inserted. It does not measure physical display latency.

| Production build, 5 MiB records | Before ms | After ms |
| --- | ---: | ---: |
| Formatted rows inserted | 36.700 | 36.500 |
| First Paint event complete | 37.016 | 36.859 |

This movement is too small to claim a repeatable paste-to-paint gain. The browser reported zero runtime exceptions. The rendered output was inspected. These tests do not establish a ranking against other JSON viewers.

## Correctness and rejected changes

Overflow values such as `1e999` become `null` in native output. Their root and nested tokens now use the null type. The retained numeric guard uses token length to avoid an extra numeric check on every float. The final float model result is +0.1% in Bun and +1.9% in Chrome; the Chrome repeat is +1.8%. This small cost supports exact token types.

The Worker state guard read an old document under virtual time. It now waits with a real clock, uses a fresh browser profile, and fails when a required condition times out. Large-source Tree, Min, indent changes, and null-source checks pass.

Rejected experiments:

- Smaller container buffers produced unstable shape timings. The established container bounds remain.
- Min tokens projected from pretty tokens depended on buffers that the Worker transfers and detaches.
- Tokenizer closure rewrites slowed numeric inputs.
- Streaming JSONL newline reads had no clear repeatable gain.
- A separate scalar container function and removal of the result closure did not establish a better container result.
- An unconditional finite-number check added about 3–5% to the Bun float model. The length guard has a smaller measured cost.
- A `Math.min` seed variant slowed medium Min inputs in Bun. The retained seed uses an integer branch; the compiler cause was not established.

## Validation and build size

All required checks pass: production build, 70 unit tests, 14 site checks, 510 fuzz documents, source state, search navigation including compressed scroll space, and zero CSP violations. The final paste gate reports **18.7 ms** minimum pipeline time and **walk/native 0.49**, below the 0.75 limit. This gate result is not a before/after speed claim.

The Mac was locked during final validation and Bun reads from Documents stalled. Checks ran on a temporary copy of the source, tests, project files, and installed dependencies. Source and test files were checked byte for byte against the workspace. Only the benchmark adapter's Git lookup used the original repository path. Browser checks used headless Chrome; Safari and Firefox were not tested.

| HTML size in bytes | Before | After | Change |
| --- | ---: | ---: | ---: |
| Raw | 74,575 | 74,312 | -263 |
| gzip level 9 | 26,167 | 26,091 | -76 |
| Brotli quality 11 | 22,012 | 21,994 | -18 |

Both versions use the same Node compression method. No dependency or lockfile change is required.

## Repeat the measurements

Run from the repository:

```sh
bun run build
bun run test
bun tests/fuzz.ts
bun run bench
bun scripts/bench-compare.ts 3d7c29a bun-isolated /tmp/pastejson-bun.json 21
bun scripts/bench-compare.ts 3d7c29a chrome /tmp/pastejson-chrome.json 41
bash scripts/verify-source-state.sh
bash scripts/verify-search-nav.sh
bash scripts/verify-csp.sh
```

For the production-build comparison, build the baseline with the same installed dependencies, then pass both `dist` directories:

```sh
baseline_dir=$(mktemp -d -t pastejson-baseline)
git archive 3d7c29a | tar -x -C "$baseline_dir"
ln -s "$PWD/node_modules" "$baseline_dir/node_modules"
(cd "$baseline_dir" && bun run build)
bun scripts/bench-browser-paste.mjs "$baseline_dir/dist" "$PWD/dist" /tmp/pastejson-browser
```

Raw samples and hashes: [Bun](2026-10-03-bun.json), [Chrome](2026-10-03-chrome.json), [Chrome repeat](2026-10-03-chrome-repeat.json), and [production browser pastes](2026-10-03-browser-paste.json). The scripts stay outside the application bundle.
